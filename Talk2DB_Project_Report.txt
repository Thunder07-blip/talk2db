SECTION 1: EXECUTIVE OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Talk2DB is a fully custom-built, intelligent, conversational analytics platform
that allows any person — regardless of their technical skill level — to ask
questions about a database in plain English and receive accurate, structured
answers within seconds.

Normally, to retrieve information from a database, someone must write "SQL"
(Structured Query Language), a specialized programming language that requires
months of study to learn correctly. Business managers who want to know "Which
are our top 5 products by revenue?" must either learn SQL themselves or wait
hours or days for an available engineer. This creates a significant bottleneck
in daily data-driven decision making.

Talk2DB eliminates this bottleneck entirely. Under the hood, it uses Large
Language Models (LLMs) — the same class of AI that powers tools like ChatGPT
— to translate a user's plain English question into perfectly formed SQL, execute
it safely against the database, and then provide a natural language summary of
the answer. The whole cycle completes in under 5 seconds.

The system was built with three core design principles:
  1. ACCURACY     — The AI must understand and correctly translate complex,
                    multi-table analytical questions into valid SQL.
  2. SECURITY     — The AI must NEVER be allowed to modify, delete, or corrupt
                    data. All queries must be strictly read-only.
  3. FLEXIBILITY  — The system must work with ANY database, not just one
                    hardcoded dataset.

All three principles have been fully achieved and verified in this project.

SECTION 2: THE PROBLEM BEING SOLVED IN DETAIL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Modern businesses store their critical data in relational databases. These are
structured stores of information where data is organized into tables, each
representing a specific entity (e.g., a Customers table, an Orders table, a
Products table, etc.). Relationships between these tables allow for powerful
cross-referencing (e.g., "Which customers ordered which products?").

The problem is that extracting insight from these databases requires writing SQL.
For example, to answer a seemingly simple question like "Find the top 5 customers
who share a city with one of our employees, ranked by total spending", an analyst
would have to write something like this:

    SELECT c.CustomerId, c.FirstName, c.LastName, c.City, SUM(i.Total) AS Spent
    FROM Customer c
    JOIN Invoice i ON c.CustomerId = i.CustomerId
    JOIN Employee e ON c.City = e.City
    WHERE c.City IS NOT NULL
    GROUP BY c.CustomerId, c.FirstName, c.LastName, c.City
    ORDER BY Spent DESC
    LIMIT 5;

This requires expertise in: table aliasing, multi-table JOIN operations, WHERE
filtering, GROUP BY aggregation, ORDER BY sorting, and LIMIT capping. A non-
technical user simply cannot write this. Talk2DB writes this automatically from
nothing more than the plain English version of the question.

Additionally, there is a serious security concern. Any system that connects an
AI to a database must ensure the AI cannot accidentally (or maliciously) issue
destructive commands like "DELETE FROM Customers" or "DROP TABLE Orders". Simple
text-matching approaches ("just check if the query starts with SELECT") are known
to be easily bypassed with tricks like comment injection or semicolon-chaining.
Talk2DB solves this with a rigorous, code-level security approach described in
detail in Section 4.

SECTION 4: THE PIPELINE — STEP BY STEP DEEP DIVE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

When a user types a question into the chat interface and hits send, the following
sequence of events happens automatically in the backend. This is the heart of
the project.

─────────────────────────────────────────────────────────────────
STEP 0: USER INPUT RECEIVED
─────────────────────────────────────────────────────────────────
The user's question arrives at the /ask HTTP endpoint in main.py. FastAPI parses
it into an AskRequest object and calls the pipeline's central ask() function.

Example question: "Which artist has the most tracks on playlists containing the
word Heavy?"

─────────────────────────────────────────────────────────────────
STEP 1: SCHEMA EXTRACTION
─────────────────────────────────────────────────────────────────
The system opens a read-only connection to the SQLite database and runs a series
of internal PRAGMA commands (SQLite's built-in metadata queries). These tell us:
  - What tables exist? (PRAGMA table_list)
  - What columns does each table have, and what data type is each column?
    (PRAGMA table_info("TableName"))
  - Which columns are Primary Keys?
  - Which columns are Foreign Keys pointing to other tables?
    (PRAGMA foreign_key_list("TableName"))

This produces a clean, typed Python object called a DatabaseSchema, which is a
list of TableSchema objects, each containing a list of ColumnSchema objects and
ForeignKeySchema objects.

For the Chinook music database, this would discover 11 tables (Album, Artist,
Customer, Employee, Genre, Invoice, InvoiceLine, MediaType, Playlist,
PlaylistTrack, Track) and their complete column definitions.

─────────────────────────────────────────────────────────────────
STEP 2: SCHEMA LINKING (THE INTELLIGENT ROUTER)
─────────────────────────────────────────────────────────────────
This is one of the most important innovations in Talk2DB. Naively, you might
think to just send the entire database schema to the AI every time. But this has
a major problem: large databases can have 100, 200, or even 500+ tables. Sending
all of them to the AI would be extremely slow, expensive, and would confuse the
AI into making mistakes.

Instead, the Schema Linker makes a fast, targeted first AI call. It sends the
complete list of table names and their columns to a special AI prompt that acts
as a "database router":

  Prompt sent to AI:
    "You are a database router. Given this question and the full list of tables,
     return ONLY a JSON array of the table names needed to answer the question.
     Example: ["Artist", "Album", "Track"]"

For our example question about artists and playlists, the AI would return:
    ["Playlist", "PlaylistTrack", "Track", "Album", "Artist"]

The linker then validates that each returned table name actually exists in the
real schema (preventing hallucinations), and the 6 unneeded tables (Customer,
Employee, Genre, Invoice, InvoiceLine, MediaType) are completely excluded from
all further processing.

─────────────────────────────────────────────────────────────────
STEP 3: CONTEXT BUILDING
─────────────────────────────────────────────────────────────────
With only the relevant tables selected, the Context Builder generates a clean,
compact text block that describes the schema in a format the SQL-generating AI
can easily parse. For example:

  DATABASE SCHEMA

  TABLE Artist
    ArtistId INTEGER [PK]
    Name NVARCHAR(120)

  TABLE Album
    AlbumId INTEGER [PK]
    Title NVARCHAR(160)
    ArtistId INTEGER [FK → Artist.ArtistId]

  TABLE Track
    TrackId INTEGER [PK]
    Name NVARCHAR(200)
    AlbumId INTEGER [FK → Album.AlbumId]
    ...

The [PK] and [FK →] annotations give the AI critical information about how
tables relate to each other, enabling it to write correct JOIN statements.

─────────────────────────────────────────────────────────────────
STEP 4: SQL GENERATION
─────────────────────────────────────────────────────────────────
The schema context and the user's original question are packaged into a carefully
engineered prompt and sent to the Groq AI model (openai/gpt-oss-120b). The
system prompt contains explicit rules for the AI:

  - Output ONLY the raw SQL query. No explanations, no markdown.
  - Only use tables and columns present in the schema provided.
  - Interpret user typos logically (e.g., "stats" means "starts").
  - Use proper JOIN syntax for multi-table questions.
  - Use aggregate functions (COUNT, SUM, AVG) when appropriate.
  - Use ORDER BY and LIMIT for "top N" type questions.
  - NEVER generate INSERT, UPDATE, DELETE, DROP, or any write operation.

The AI temperature is set to 0.0, which means the output is deterministic —
it will generate the same answer every time for the same input, not a random one.

For our example, the AI would generate:
  SELECT a.Name
  FROM Artist a
  JOIN Album al ON al.ArtistId = a.ArtistId
  JOIN Track t ON t.AlbumId = al.AlbumId
  JOIN PlaylistTrack pt ON pt.TrackId = t.TrackId
  JOIN Playlist p ON p.PlaylistId = pt.PlaylistId
  WHERE p.Name LIKE '%Heavy%'
  GROUP BY a.ArtistId, a.Name
  ORDER BY COUNT(*) DESC
  LIMIT 1

This is a 5-table JOIN with a WHERE filter, GROUP BY, ORDER BY, and LIMIT — a
genuinely complex query that even experienced SQL writers might take 5-10 minutes
to write carefully.

After receiving the raw text from the AI, the system cleans it:
  - If the AI added markdown backticks (```sql ... ```), they are stripped.
  - If the AI returned multiple statements separated by semicolons, only the
    first one is kept.

─────────────────────────────────────────────────────────────────
STEP 5: AST SECURITY VALIDATION
─────────────────────────────────────────────────────────────────
Before the SQL is allowed anywhere near the database, it goes through the
most important security layer in the entire project: the AST Validator.

"AST" stands for Abstract Syntax Tree. Just like how English grammar can be
diagrammed into a tree of subjects, verbs, and objects, SQL can be parsed into
a tree of its logical components. The `sqlglot` library does this parsing.

Example: The query "SELECT * FROM Artist; DROP TABLE Artist" would produce an
AST with TWO top-level nodes — one SELECT node and one DROP node. The validator
immediately detects this and rejects it.

The validator performs three levels of checking:

  LEVEL 1 — Parse Check:
  "Can the SQL even be parsed into valid SQLite syntax?" If not, it is rejected
  as malformed SQL.

  LEVEL 2 — Multi-Statement Check:
  "Does the query contain more than one statement?" The validator calls
  sqlglot.parse() which returns a LIST of statements. If that list contains
  more than one item, it immediately returns: "Multiple SQL statements are not
  allowed." This blocks the classic attack of hiding a DROP command after a
  semicolon.

  LEVEL 3 — Node Type Check:
  "Is the top-level statement a SELECT?" If not (e.g., it's an INSERT or UPDATE),
  it is rejected as: "Only SELECT queries are allowed."

  LEVEL 4 — Deep AST Inspection:
  Even if the top-level statement is a SELECT, the validator walks EVERY SINGLE
  NODE in the entire syntax tree, looking for the following node types hidden
  anywhere inside: Insert, Update, Delete, Drop, Alter, Create, Command,
  Commit, Rollback, Transaction.

  This catches extremely sophisticated edge cases, for example, a SELECT
  statement that contains a subquery or CTE (Common Table Expression) which
  itself contains a write operation. No amount of cleverness can hide a write
  node from the full AST scan.

Only if all four levels pass does the SQL proceed to execution.

─────────────────────────────────────────────────────────────────
STEP 6: EXECUTION WITH AUTO-CORRECTION LOOP
─────────────────────────────────────────────────────────────────
The validated SQL is sent to the QueryService, which opens a read-only database
connection and executes the query. The system also records the exact execution
time in milliseconds.

However, even with a perfectly structured SQL query, the database might throw an
error. The most common example is when the AI slightly misnames a column. For
instance, if the database has "SupportRepId" but the AI wrote "SupportId",
SQLite would throw: "no such column: SupportId".

Without self-correction, the entire pipeline would fail and return an error to
the user. Instead, Talk2DB implements a correction loop of up to 3 attempts:

  ATTEMPT 1: Generate and run the SQL query normally.
  
  IF IT FAILS: Build a correction prompt that includes:
    - The original database schema context.
    - The user's original question.
    - The BAD SQL that was generated on the previous attempt.
    - The EXACT DATABASE ERROR MESSAGE.
    
  ATTEMPT 2: Send the correction prompt to the AI. The AI reads the error
  message and fixes its own mistake.
  
  IF IT FAILS AGAIN: Repeat with ATTEMPT 3.
  
  IF ALL 3 ATTEMPTS FAIL: Return the final error to the user with full details.

This self-correction loop makes the system dramatically more robust in practice.
It also handles cases where users have severe typos in their questions that
confused the AI into picking a slightly wrong column name.

─────────────────────────────────────────────────────────────────
STEP 7: CONVERSATIONAL SUMMARY GENERATION
─────────────────────────────────────────────────────────────────
Once the data is successfully retrieved from the database, raw rows of data
are returned. For our example, the raw result would be:

  Name
  ----
  Metallica

While this is the correct answer, Talk2DB adds a final step that transforms the
data into a human-friendly answer. It sends a third AI call with a summary prompt:

  "You are a helpful data analyst. Given the user's question, the SQL used,
   and a sample of the result data, provide a 1-3 sentence summary of the
   answer. Do NOT explain the SQL. Just answer the question."

The AI reads the data and writes: "Metallica has the most tracks in playlists
whose names include the word 'Heavy'."

This makes the experience feel like talking to a real data analyst, not just
looking at a raw database query tool.

─────────────────────────────────────────────────────────────────
STEP 8: RESPONSE RETURNED TO THE FRONTEND
─────────────────────────────────────────────────────────────────
The pipeline returns a complete, structured JSON object called a Talk2DBResult:
  - question       : The original user question.
  - generated_sql  : The final, validated SQL query.
  - query_result   : The data rows, column names, row count, execution time,
                     and a flag indicating if the results were truncated.
  - summary        : The conversational natural-language answer.
  - success        : Boolean: did the pipeline succeed?
  - total_time_ms  : Total wall-clock time for the entire operation.
  - llm_time_ms    : Time spent specifically on AI calls.
  - retries        : How many correction attempts were needed (usually 0).
  - linked_tables  : Which tables the schema linker decided to use.

SECTION 5: THE WEB API — HOW THE FRONTEND COMMUNICATES WITH THE BACKEND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The backend exposes a REST API built with FastAPI. These are the endpoints:

  GET  /
    Returns the main index.html web application. This is the page the user
    sees when they open the browser.

  GET  /tables
    Returns a simple JSON list of all table names in the current database.
    Example response: { "tables": ["Artist", "Album", "Track", ...] }

  GET  /schema/full
    Returns the complete database schema as a detailed JSON object, including
    all tables, all columns with their data types, primary key flags, and all
    foreign key relationships. The frontend's sidebar uses this endpoint to
    render the interactive schema explorer.

  GET  /schema/{table_name}
    Returns the detailed column and foreign key information for one specific
    table. Used when a user clicks on a table in the sidebar.

  POST /query
    Accepts a raw SQL string and executes it directly (after AST validation).
    This endpoint exists for developers and power users who want to run their
    own SQL without going through the NL pipeline.

  POST /ask
    This is the primary endpoint used by the chat interface.
    Accepts: { "question": "Who are the top 5 customers?" }
    Returns: The full Talk2DBResult JSON object with SQL, data, and summary.

SECTION 6: THE FRONTEND — THE USER INTERFACE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The entire user interface is built into a single HTML file (app/static/index.html)
using a CDN-based approach. This means there is NO separate build step, no
Node.js required, and no complex npm setup. The server simply serves the HTML
file and the browser downloads React and Tailwind CSS directly from public CDNs.

The UI is composed of three main sections:

  LEFT SIDEBAR — DATABASE SCHEMA EXPLORER
    On startup, the frontend calls GET /schema/full and dynamically renders
    every table and its columns as a collapsible list. Primary Key columns are
    annotated with a blue "PK" label. This gives the user an instant visual
    map of the database they are querying.

  MAIN CHAT AREA — CONVERSATION HISTORY
    The chat area shows the full conversation history in a messaging-app style.
    User questions appear in dark bubbles on the right side. AI responses
    appear in white cards on the left side.

    Each AI response card contains multiple sub-sections:
      a) META STATS BAR: Shows the total execution time in milliseconds, the
         number of rows returned, and the number of correction retries (if any).
      b) GENERATED SQL: The exact SQL query that was executed, displayed in a
         dark code block with monospace font for readability.
      c) ANSWER SUMMARY: The conversational natural-language summary in a blue
         highlighted box. This is what non-technical users primarily read.
      d) DATA RESULTS TABLE: A horizontally and vertically scrollable table
         showing the raw data with sticky column headers. If the results are
         truncated to 100 rows, a warning notice is shown.

  BOTTOM INPUT BAR — THE QUERY INPUT
    A text input field with a send button. Also includes one-click example
    prompt chips ("Top 5 customers", "Popular genres") for new users to get
    started quickly without knowing what to type.

  OVERFLOW HANDLING:
    A specific fix was implemented to handle wide result tables. When a query
    returns many columns (e.g., 10+ columns), the table could overflow the screen
    width. The fix applies CSS 'min-w-0' and 'overflow-hidden' constraints to the
    message bubble containers, ensuring that the 'overflow-x-auto' scrollbar on
    the table container activates correctly and the page layout never breaks.

SECTION 7: MULTI-DATABASE SUPPORT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A critical feature of Talk2DB is that it is not locked to one specific database.
The schema extraction layer was designed to be fully dynamic — it reads the
structure of whatever database it is connected to at runtime using standard
SQLite PRAGMA commands. There is no hardcoded table name or column name anywhere
in the application code.

To switch databases, a user sets a single environment variable before starting
the server:

  TALK2DB_DB_PATH=/path/to/your_database.db uvicorn app.main:app

The application will:
  1. Read the new database path from the environment variable.
  2. Connect in read-only mode.
  3. Discover all tables, columns, and relationships automatically.
  4. Serve the frontend with the new schema in the sidebar.
  5. Route all AI calls using the new schema context.

This was demonstrated by switching from the Chinook music database (11 tables)
to a custom Company database (2 tables: Employee and Department). The application
adapted instantly with no code changes required.

Sample databases included:
  data/chinook.db  — A realistic music store database with 11 interconnected
                     tables covering artists, albums, tracks, playlists,
                     customers, invoices, and employees.
  data/company.db  — A small HR database with an Employee table (Id, Name,
                     Salary, DepartmentId) and a Department table (Id, Name).

SECTION 11: SECURITY DESIGN — IN DEPTH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Security was a primary concern throughout this project. Three independent layers
of protection exist, each acting as a separate defense:

LAYER 1 — SYSTEM PROMPT RULES
  The AI is instructed from the very beginning in its system prompt: "Never
  generate INSERT, UPDATE, DELETE, DROP, ALTER, or any write operation." This
  is the first, softest layer. While an AI model generally follows instructions,
  it is not reliable enough on its own because it can occasionally hallucinate
  or be manipulated by a specially crafted user question (this is called
  "prompt injection").

LAYER 2 — AST VALIDATION (sqlglot)
  This is the hard enforcement layer. Regardless of what the AI generates,
  every SQL string is parsed into an Abstract Syntax Tree and every single
  node is inspected before execution. The following are hard-blocked at the
  code level: Insert, Update, Delete, Drop, Alter, Create, Command, Commit,
  Rollback, Transaction nodes. Multiple statements are also hard-blocked.

  This layer is completely AI-independent. Even if the AI went completely
  rogue and decided to generate destructive SQL, the AST validator would
  catch and reject it before any data is touched.

LAYER 3 — READ-ONLY DATABASE CONNECTION
  The connection to the SQLite database is opened using the URI:
  "file:path.db?mode=ro"
  
  This is enforced at the SQLite driver level, deep inside the C library
  that SQLite is built on. Even if a query somehow bypassed both Layer 1
  and Layer 2, the database connection itself is physically incapable of
  executing a write operation. It would return a "SQLITE_READONLY" error.

This defense-in-depth approach (multiple independent layers, each catching
what the previous might miss) is the same strategy used in enterprise-grade
security systems.

SECTION 13: HOW TO RUN THE PROJECT LOCALLY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Requirements: Python 3.12+, Git, a Groq API key.

  Step 1: Clone the repository
    git clone https://github.com/Thunder07-blip/talk2db.git
    cd talk2db

  Step 2: Create a virtual environment
    python3 -m venv .venv
    source .venv/bin/activate       (Linux/Mac)
    .venv\Scripts\activate          (Windows)

  Step 3: Install all dependencies
    pip install -r requirements.txt

  Step 4: Create the .env file with your API key
    Create a file named ".env" in the root of the project with this content:
      groq_api_1=your_actual_groq_api_key_here
      TALK2DB_DB_PATH=data/chinook.db

  Step 5: Start the server
    uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

  Step 6: Open the chat interface
    Open your web browser and go to: http://127.0.0.1:8000
    You should see the Talk2DB chat interface with the Chinook schema
    in the left sidebar. Start asking questions!

  To use a different database:
    Replace "data/chinook.db" in the .env with the path to your .db file,
    then restart the server. The system adapts automatically.

  To run the automated tests:
    .venv/bin/python -m unittest discover -s tests -p "test_*.py"

  To run the benchmark:
    .venv/bin/python benchmark.py
